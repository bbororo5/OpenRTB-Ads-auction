# 제품·도메인 요구사항

상태: 확정안

수치와 합격 기준: [부하·데이터·검증 기준](workload.md)

이 프로젝트는 웹 배너 RTB에서 제한 시간 경매, 캠페인 선택과 페이싱, 분산 예산 정합성, 장애 지속성을 구현·검증한다.

## 1. 범위

| 역할 | 책임 |
|---|---|
| 공급자 | 광고 기회를 요청하고 경매 결과를 받는다. k6가 모의한다. |
| 광고 표시 클라이언트 | 낙찰 광고를 표시하고 렌더링 성공을 SSP에 통지한다. 통합 시험이 모의한다. |
| SSP | 요청 검증, DSP 호출, 슬롯별 낙찰, 렌더링 검증과 과금 가능 사건의 통지를 담당한다. |
| 프로젝트 DSP | 캠페인·소재·예산으로 입찰하고 잠재 지출을 확정·해제·만료한다. |
| 외부 DSP | 경쟁 조건을 만드는 독립 모의 DSP다. |
| 광고주 | 프로젝트 DSP에 캠페인과 총예산을 맡긴다. |

공급자, SSP, 프로젝트 DSP, 두 외부 DSP는 서로 다른 회사다. SSP에서 보면 셋 모두 독립된 DSP 회사이며 같은 경매·통지 계약을 따른다. 프로젝트 DSP만 내부를 제품 수준으로 구현하며, 여러 인스턴스가 하나의 논리적 캠페인 예산을 공유하고 게이트웨이 뒤에서 동작한다. 외부 DSP는 각 회사의 독립 모의 주소이며 이 게이트웨이를 사용하지 않는다. 외부 DSP의 리전·AZ 배치, 예산과 장애 복구는 구현·평가 범위가 아니다.

SSP는 경매 결과와 과금 가능한 렌더링 사건의 권위자이고, 프로젝트 DSP는 캠페인과 광고주 예산의 권위자다. 두 회사는 독립 배포·독립 저장소를 사용하며 상대 저장소나 내부 원장을 호출하지 않는다. SSP는 과금 가능 사건을 자기 청구 근거로 기록하고, DSP는 기한 안에 실제로 받은 `burl`만 광고주 캠페인 지출 근거로 기록한다. 통지 유실로 생긴 미과금은 허용하되 광고주에게 추측·중복 과금하지 않는다.

SSP와 프로젝트 DSP의 핵심 경로는 제품 수준으로 구현한다. 공급자 애플리케이션, 광고 표시 SDK, 실제 브라우저, 외부 DSP 내부는 구현하지 않는다.

다음은 범위 밖이다.

- 클릭·기여 추적, 사용자 식별·프로파일링, 세부 타기팅
- 캠페인 관리 화면과 실행 중 예산·입찰가·기간 변경
- 머신러닝 입찰 최적화, 성과 예측, 고급 페이싱, 빈도 제한
- 광고 사기·가시성·소재 심사·브랜드 안전성
- 복수 통화, 충전·환불·청구서·은행 송금·세금·매체사 지급과 분쟁 조정
- 쿠버네티스, 자동 확장 제어면

## 2. 요구사항

### `요구-01` 제한 시간 경매

SSP는 요청을 검증하고 프로젝트 DSP와 두 외부 DSP에 의미상 같은 OpenRTB 2.6 요청을 병렬로 보낸다. DSP별 결과는 `VALID_BID`, `NO_BID`, `TIMEOUT`, `INVALID_BID`, `ERROR` 중 하나로 끝난다. 정상 시험에서 외부 DSP는 프로젝트 DSP의 기대 낙찰률이 20~28%가 되도록 입찰 참여율·CPM·지연·오류를 설정한다.

- 요청은 하나 이상의 광고 슬롯을 가질 수 있고 각 슬롯은 독립된 경매·낙찰·과금 단위다.
- `입찰 마감 = SSP 요청 수신 시각 + 유효 tmax`이며 마감 뒤 응답은 결과를 바꾸지 않는다.
- 슬롯별 유효 입찰 중 최저가 이상인 최고 CPM이 낙찰한다.
- 1가격 경매를 사용하며 낙찰 CPM은 DSP가 제출한 CPM과 같다.
- 같은 CPM이면 `dspId`, 그다음 `bidId`의 오름차순으로 낙찰자를 정한다.
- 최고가 동률은 도착 순서나 고정 DSP 우선순위가 아니라 경매·슬롯 식별자를 이용해 결정적으로 분산한다.
- 한 DSP가 실패해도 다른 유효 입찰로 경매를 끝내며 유효 입찰이 없으면 정상적인 광고 없음으로 응답한다.
- 동일한 `auctionId + impressionId`는 최대 한 낙찰과 한 과금 결과만 만든다.
- 계약된 공급자는 요청마다 고유한 `providerRequestId`와 요청 안에서 고유한 슬롯 ID를 보내고, 같은 광고 기회를 재시도할 때 두 값을 바꾸지 않는다. SSP는 지역 메모리의 공급자 설정 스냅숏으로 공급자 ID·키 ID·활성 상태를 검증한다.
- SSP는 인증된 공급자 식별자와 `providerRequestId`로 동일 요청을 판정한다. 같은 ID와 같은 내용의 중복 요청은 최초 결과를 재사용하고, 같은 ID의 내용이 달라지면 거부한다.
- 중복 공급자 요청은 새 DSP 호출·캠페인 선택·잠재 지출·낙찰·과금을 만들지 않는다.

### `요구-02` 캠페인 입찰과 생명주기

프로젝트 DSP는 슬롯마다 최대 한 캠페인과 소재를 선택해 하나의 입찰을 반환한다.

입찰 후보는 다음 조건을 모두 만족해야 한다.

- 현재 시각이 캠페인의 시작·종료 기간 안이고 캠페인이 활성 상태다.
- 소재의 형식과 크기가 슬롯에 맞는다.
- 입찰 금액의 잠재 지출을 만들 수 있다.
- 기본 페이싱 정책이 현재 입찰을 허용한다.

후보가 여러 개면 페이싱 목표보다 가장 뒤처진 캠페인을 선택하고, 같은 상태면 `campaignId` 순으로 결정한다. 적격 후보가 없으면 `NO_BID`한다. 이용자·지역·행동·매체 분류 타기팅은 다루지 않는다.

캠페인은 시험 전에 식별자, 활성 상태, 총예산, 고정 입찰 CPM, 시작·종료 시각과 소재를 등록한다. 실행 중에는 활성 상태를 포함한 캠페인 값을 변경하지 않는다. 비활성 상태이거나 종료 시각이 지난 캠페인은 새 입찰을 만들지 않으며 이미 만든 잠재 지출은 원래 규칙대로 종결한다.

동일한 DSP 요청을 다시 받으면 최초 캠페인·소재·가격·`bidId`와 잠재 지출을 재사용한다. 최초 결과를 안전하게 확인할 수 없으면 새 입찰을 만들지 않고 `NO_BID`한다.

### `요구-03` 가격과 캠페인 예산

통화는 KRW 하나이며 입찰가와 최저가는 CPM이다.

- CPM은 소수점 셋째 자리까지 허용하고 초과 정밀도는 거부한다.
- 노출 1건 금액은 `CPM / 1,000`으로 정확하게 보존한다.
- 입찰·잠재 지출·과금 과정에서 반올림하지 않는다.
- 내부 자료형과 실제 대금 정산의 반올림은 이후 결정 범위다.

캠페인에는 하나의 총예산만 있다.

```text
캠페인 확정 지출 + 유효한 잠재 지출 <= 캠페인 총예산
```

프로젝트 DSP는 입찰을 반환하기 전에 슬롯별 입찰 금액의 잠재 지출을 만든다. 한 캠페인이 같은 요청의 여러 슬롯에 입찰하면 모든 잠재 지출의 합을 검사한다. 예산이 정확히 소진되는 것은 허용하지만 초과 지출은 허용하지 않는다.

| 사건 | 금액 효과 |
|---|---|
| 입찰 제시 | DSP 예약 시각부터 노출 1건 금액을 잠재 지출로 잡는다. |
| `nurl` | 잠재 지출을 유지한다. |
| `lurl` | 만료 전에 접수하면 잠재 지출을 해제한다. |
| `burl` | 만료 전에 DSP 지역 장부에 내구 기록하면 잠재 지출을 확정 지출로 바꾼다. |
| 처리 주체·인스턴스·배치 변경 | 새 예약의 처리 주체는 바뀔 수 있지만 이미 만든 잠재 지출은 바꾸지 않는다. |
| 만료 | 다른 결과 없이 예약 후 5초가 지나면 잠재 지출을 해제한다. |
| 늦은 `burl` | 기록만 남기고 금액을 바꾸지 않는다. |

정상 렌더링은 SSP 경매 결정 후 p99 500ms 안에 끝내고, 실제 노출 유효 상한은 2초로 둔다. DSP 예약은 SSP의 `burl` 전달과 짧은 장애·재시도를 포함해 예약 시각부터 5초 유지한다. DSP가 복구 가능하게 접수한 시각으로 기한을 판정하며, 입찰 응답이 SSP에 도착하지 않은 잠재 지출도 같은 5초 안에 끝난다.

SSP는 각 슬롯의 예상 노출 상한을 표준 `Imp.exp=2`로 요청에 넣고, 프로젝트 DSP는 허용하는 노출 지연을 표준 `Bid.exp=2`로 응답한다. 두 값은 OpenRTB상 권고 신호이지만, 이 프로젝트의 SSP–DSP 통합 계약에서는 2초 뒤의 렌더링을 청구 근거로 만들지 않는 기준으로 적용한다. `burl`의 전달·접수 상한은 별도 전용 필드가 아니라 같은 통합 계약의 5초 예약 기한으로 정한다. 이는 렌더링 증표의 2초 유효 기한과 다르다.

같은 사건은 여러 번 전달되어도 금액에 한 번만 영향을 준다. 모순된 `lurl`과 `burl`은 정상 입력이 아니라 계약 결함이며 DSP는 금액을 다시 변경하지 않고 격리한다.

예약 처리 주체·인스턴스·배치가 바뀌어도 이미 만든 잠재 지출은 `lurl`, `burl`, 5초 만료 중 하나로 끝날 때까지 캠페인 예산을 계속 점유한다. 장애로 사용 내역을 확신할 수 없으면 초과 지출을 막기 위해 사용 가능성이 있는 금액을 보수적으로 점유하며, 미사용임을 복구 가능하게 증명하거나 잠재 지출 가능 시간이 끝난 뒤에만 가용 예산으로 반환한다.

5초 뒤의 `burl`은 광고주 캠페인 금액을 바꾸지 않는다. 이때 SSP와 프로젝트 DSP 사이에 발생할 수 있는 지급·손실과 회계 대사는 구현 범위 밖이며, 광고주 예산 원장과 섞지 않는다.

### `요구-04` 기본 페이싱

캠페인 총예산을 초과하지 않으면서 시작부터 종료까지 지나치게 일찍 소진되지 않게 한다.

- 기본 목표는 기간에 비례하는 선형 누적 지출이다.
- 목표보다 앞선 캠페인의 입찰 참여를 줄이고 뒤처진 캠페인을 우선한다.
- 적격 광고 기회가 충분하면 기간 전체에 걸쳐 예산을 소비해야 한다.
- 적격 광고 기회가 부족한 경우 미소진은 허용한다.
- 각 리전은 자기 책임액을 기간에 맞춰 단기 리스로 공급한다. 리스 크기·유효 기간·보충 임계치와 허용 편차는 검증 기준에서 구체화한다.

### `요구-05` 렌더링과 통지

DSP는 입찰 응답에 사전 등록된 `nurl`, `lurl`, `burl`을 제공한다. SSP는 경매 응답 경로 밖에서 비동기로 호출한다.

- 프로젝트의 SSP 연동 프로필은 OpenRTB `burl`을 지원한다. 실제 업체 연동 전에는 지원 여부와 과금 발생 조건을 확인하며 사설 응답 규격으로 보완하지 않는다.
- DSP는 표준 `Bid.exp`에 실제 노출 유효 상한인 2초를 넣는다. DSP 내부 예약은 통지 전달과 짧은 복구 여유를 포함해 5초 유지한다.
- SSP가 낙찰을 결정하면 `nurl`, 패찰을 결정하면 `lurl`을 보낸다.
- 정상 렌더링 목표는 SSP 낙찰 결정부터 p99 500ms이며, 실제 노출 유효 상한은 2초다.
- 렌더링 증표는 공급자 ID·공급자 요청 ID·슬롯 ID, 발급 리전·발급 시각·2초 기한, 낙찰 DSP·가격·`burl`을 AEAD로 봉인한 프로젝트 전용 값이다. OpenRTB 객체나 DSP 계약에 이 증표를 추가하지 않는다.
- SSP가 2초 안에 유효한 렌더링 증표를 접수하면 지역 기록에 청구 근거와 `burl` 전달 작업을 함께 추가한 뒤 성공을 응답한다. `burl`은 그 뒤 비동기로 보낸다.
- 렌더링 청구 시에는 증표의 공급자 귀속을 검증하고, 지역 공급자 설정 스냅숏에서 해당 공급자가 여전히 활성 상태인지 다시 확인한다.
- DSP가 예약 후 5초 안에 `burl`을 지역 기록에 내구 접수해야 캠페인 과금이 확정된다.
- 렌더링되지 않은 낙찰을 위한 별도 미과금 통지는 보내지 않는다.
- DSP는 `burl` 내부 사건을 커밋한 뒤 본문 없는 일반 HTTP 성공을 반환한다. 응답 객체·전용 헤더·접수 증표를 추가하지 않으며 SSP는 DSP 내부 사건을 해석하지 않는다.
- OpenRTB는 SSP의 재시도를 보장하지 않는다. 같은 URL이 다시 호출되면 DSP는 금액을 다시 바꾸지 않지만, 통지가 끝내 오지 않으면 예약을 만료하고 광고주에게 과금하지 않는다.
- `burl`은 실제 송금 요청이 아니다. 청구서·송금과 업체 간 회계 대사는 범위 밖이다.
- 확정 지출은 사건마다 지역 예산 원장에 쓰지 않고 모든 잠재 지출 기한이 끝난 리스의 소비·반환액으로 한 번 정산한다.
- 정상 상황에서 SSP의 청구 근거 생성부터 DSP의 복구 가능한 접수까지 p99는 1초 이하다.

SSP의 접수 시각으로 2초 경계를 판정하며 클라이언트가 주장한 시각은 관측에만 쓴다. 외부 입력의 가격·캠페인·과금 주장을 믿지 않고 SSP가 실제로 만든 낙찰 결과와 연결된 통지만 인정한다. 중복·변조·재사용된 통지는 추가 과금을 만들 수 없다.

### `요구-06` 부분 실패와 과부하

- 외부 DSP 하나의 실패는 해당 입찰에만 영향을 주고 SSP 경매는 계속한다.
- 프로젝트 DSP가 예산을 안전하게 예약할 수 없으면 기술 실패 또는 `NO_BID`로 끝내고 예산을 추측하지 않는다.
- SSP가 경매 결과의 인증된 렌더링 증표를 만들 수 없거나 렌더링 청구 사건을 지역 기록에 append할 수 없으면 해당 성공을 반환하지 않는다.
- 프로젝트 DSP의 통지 접수가 일시적으로 불가능하면 이미 발급한 예산 한도 안에서만 동작하고 미과금 위험 상한을 넘기기 전에 새 입찰을 중단한다. SSP는 가능한 경우 외부 DSP와 경매를 계속한다.
- 처리 능력을 넘은 요청은 광고 없음으로 숨기지 않고 명시적인 기술 실패로 빠르게 거절한다.
- 과부하에서도 잘못된 낙찰, 예산 초과와 중복 과금은 허용하지 않는다. 지역 재해의 미복제 SSP 청구 손실은 기록하고 광고주에게 추측 과금하지 않는다.

### `요구-07` 장애 지속성과 상태 보존

SSP 회사와 프로젝트 DSP 회사는 각각 서울(`ap-northeast-2`)과 도쿄(`ap-northeast-1`) AWS 리전에 여러 인스턴스를 둔다. 각 리전은 여러 AZ에 배치한다. 프로젝트 DSP 게이트웨이와 예산 원장도 인스턴스·AZ·리전 하나가 전역 단일 장애점이 되면 안 된다.

- 공급자는 전역 SSP 경매 주소 하나만 호출하며 리전을 선택하지 않는다. SSP 전역 진입 계층은 요청 출발 네트워크와 정상 상태를 기준으로 서울 또는 도쿄의 SSP 셀을 선택한다.
- 인스턴스·AZ·리전 하나가 중단되어도 다른 리전은 경매를 계속하고, 프로젝트 DSP는 안전하게 증명할 수 있는 예산 권한 안에서 입찰을 계속한다.
- 장애 영역에만 속한 캠페인·예산 권한의 일시적 사용 중단은 허용하지만 다른 캠페인과 외부 DSP까지 중단시키지 않는다.
- SSP 경매·청구와 프로젝트 DSP 입찰은 같은 지역에서 처리한다. SSP는 경매 응답에 발급 리전 전용 렌더링 통지 URL을 넣는다. 클라이언트는 이 URL을 그대로 호출하며, 증표와 청구 사건은 발급 리전에 귀속한다. 다른 SSP 리전은 이를 대신 청구하지 않는다. 리전 재해의 최근 사건 손실은 회사별 손실 정책으로 처리한다.
- 프로젝트 DSP는 같은 통지 URL의 중복 호출에서 캠페인 금액 효과를 한 번만 만든다. `lurl` 유실과 오지 않은 `burl`은 5초 만료가 안전하게 종결한다.
- 진행 중 경매 계산은 실패할 수 있지만 이미 생성한 잠재 지출은 5초 안에 종결한다.
- 복구 뒤 중복 전달이 발생해도 낙찰과 금액 효과는 바뀌지 않는다.
- SSP와 DSP는 상대 저장소나 내부 장부를 조회하지 않는다. 외부 계약은 OpenRTB 통지 URL과 일반 HTTP 응답뿐이며, DSP는 재호출에 안전하지만 SSP의 재시도를 전제하지 않는다.
- 리전 장애 중 사용 여부를 증명할 수 없는 예산은 다른 리전에 즉시 재할당하지 않는다. 복구하거나 최대 잠재 지출 기한이 끝날 때까지 보수적으로 점유한다.
- 공급자 설정의 쓰기 권위는 서울 PostgreSQL에 하나만 둔다. 설정 테이블은 도쿄 PostgreSQL에 비동기 논리 복제하며, 각 SSP는 자기 리전의 버전형 스냅숏을 메모리에 적재해 요청마다 사용한다.
- 신규 공급자와 일반 설정 변경은 먼저 동기화된 리전부터 효력이 생겨도 된다. 리전별 설정 버전·전파 지연은 관측하지만 전역 활성화 장벽은 두지 않는다.
- 키 회전은 구·신 키를 겹쳐 허용한다. 긴급 비활성화 전파가 정한 상한을 넘겨 늦어진 리전은 해당 공급자의 요청만 보수적으로 거부한다.

### `요구-08` 검증과 통신 독립성

경매, 캠페인 선택, 페이싱, 금액 상태, 자원 포화와 장애 전환을 연결해 관측하고 같은 조건으로 재현할 수 있어야 한다. JSON을 이진 표현으로 바꾸어도 경매·금액 의미와 합격 기준은 달라지지 않는다.

## 3. 제약과 가정

- SSP–DSP 계약은 OpenRTB 2.6의 명시적 하위 규격을 따른다.
- `burl` 지원과 과금 가능 사건의 의미는 SSP 연동 전 확인할 기능이며 응답 본문·전용 헤더·재시도 의무를 추가하지 않는다.
- 공급자 API는 프로젝트 전용이며 OpenRTB 객체를 직접 노출하지 않는다.
- 공급자 계약 관리 화면과 인증 수단의 발급은 구현하지 않는다. 시험용 공급자 설정은 PostgreSQL에서 버전·복제하고, SSP는 로컬 스냅숏의 공급자 ID·키 ID·활성 상태를 검증한다.
- 웹 배너, KRW, 1가격 경매를 우선한다.
- 실행 환경은 Java 21과 서울(`ap-northeast-2`)·도쿄(`ap-northeast-1`) AWS 리전이다.
- HTTP/JSON은 초기 표현일 뿐 영구 제약이 아니다.
- 실제 사람이 광고를 보았는지 판별하는 광고 사기 탐지는 하지 않는다. 유효한 낙찰과 연결된 클라이언트 통지를 렌더링 성공으로 간주한다.
- 구현이 어렵다는 이유로 예산 불변식, 50ms 목표 또는 장애 범위를 낮추지 않는다. 요구를 바꾸려면 ADR이 아니라 이 문서부터 바꾼다.
