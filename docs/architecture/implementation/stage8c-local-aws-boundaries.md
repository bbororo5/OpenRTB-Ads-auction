# 로컬 진단과 AWS 검증의 책임 분리

## 현재 위치

SSP·DSP와 실제 DB를 연결한 로컬 관찰 환경을 마련했다. 이는 Stage8C의 반복 진단 기반이며,
500 RPS·10분, 1,000 RPS 과부하, 물리적 장애 격리의 최종 합격 선언이 아니다.

| 로컬에서 반복 | AWS에서 별도로 확인 |
|---|---|
| 기능 스모크, 요청 실패 재현 | 배포·인증·네트워크 구성 |
| 요청 → trace → 지표·로그 대조 | 서로 다른 호스트 사이 지연 |
| 최소 변경 전후 같은 조건 비교 | 물리적으로 분리한 최대 처리량·과부하·회복 |
| 실행기 실패와 증거 보존·종료 | 인스턴스·AZ 장애 격리와 비용 안전장치 |

로컬에서는 k6·DB·앱·관찰 도구가 같은 Linux VM 자원을 공유한다.
로컬 p99를 AWS p99로, 로컬 최대 RPS를 운영 용량으로 대체하지 않는다.
또한 진단 실행의 강제 sampled trace와 요청 journal은 관측 오버헤드를 추가한다.

## 이번 작업에서 바꾸지 않은 것

- SSP·DSP의 업무 처리·동시성·예산 알고리즘.
- k6의 기존 업무·성능 임계값.
- AWS 배포·OIDC·정리 정책. AWS 실행은 하지 않았다.
- OpenTelemetry Java agent의 metrics/traces/logs 기능.

eBPF 프로파일러는 선택적 실행 경로를 유지했다. 이번 실제 검증 범위는
metrics·trace와 합성 로그 전송이며, profile 수집 및 실제 애플리케이션 로그의
모든 경로가 검증됐다고 주장하지 않는다.

## 다음 사용자 참여 단계

1. [실행 안내](stage8c-local-runbook.md)에 따라 로컬 환경을 열고 사용자가 화면을 확인한다.
2. 첫 스모크의 504 또는 재현된 느린 요청을 하나 고른다.
3. 동일 trace의 SSP·DSP·DB 구간과 정상 요청의 차이를 사용자가 먼저 읽는다.
4. 관찰한 사실, 가설, 반증할 측정을 구분해서 적는다.
5. 가설을 확인한 다음에만 최소 변경을 구현하고 같은 조건으로 재시험한다.

첫 smoke 실패와 이후 독립 verify 통과는 동일 준비 조건의 A/B 실험이 아니다.
“초기화가 원인”이라는 가설은 세울 수 있지만 아직 결론은 아니다.
증거 보존 덕분에 다음 분석을 시작하기 위해 AWS를 다시 배포할 필요는 없다.

구현은 `docker-compose.local.yml`(선언적 배치), `lib/local-session.ts`(수명주기),
`lib/local-evidence.ts`(시험·증거 조립)로 책임을 나눈다. 순수 journal·trace 해석은
기존 `lib/request-evidence.ts`를 재사용하며 원격 SSM 실행은 로컬 경로에서 호출하지 않는다.
