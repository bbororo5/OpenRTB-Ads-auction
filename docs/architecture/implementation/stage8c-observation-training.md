# 다음 세션: 사용자가 증거를 읽는 인과관계 추적 훈련

## 시작 조건

오늘의 배포는 철거됐다. 먼저 로컬에 보존한 자료를 읽으며 시작한다. 새 배포나 비용 발생 작업은 이 문서만으로 자동 실행하지 않는다.

원본 자료 위치는 `docs/evidence/performance/2026-09-03/`이며 아직 Git에 올리지 않은 로컬 증거다. 현재 보존물은 k6 결과, 컨테이너 CPU/메모리 표본, CloudWatch 조회 결과, gateway/DB 스냅샷과 로컬 재현 자료다. Grafana 화면이나 전체 trace/log/profile 저장소를 백업한 것은 아니다. 당시 대시보드를 그대로 다시 열 수 있다고 가정하지 않는다.

## 진행 방식

사용자가 먼저 자료를 열고 관찰을 말한다. AI는 한 번에 한 질문만 제시하고 답을 기다린다. 그 다음 관찰 사실과 해석을 분리하고, 다음에 볼 증거를 함께 고른다. 전체 원인이나 수정안을 먼저 설명하지 않는다.

매 단계는 아래 네 문장으로 정리한다.

- 관찰: 어느 파일의 어느 값이 어떻게 바뀌었는가?
- 가설: 그것을 설명하는 원인은 무엇인가?
- 대안: 같은 현상을 설명할 다른 원인은 무엇인가?
- 반증: 어떤 자료가 나오면 내 가설을 버릴 것인가?

## 증거를 여는 순서

### 1. 사용자 요청의 성공과 DSP의 정상 동작을 구분하기

`stage8c-aws-rtb-capacity-20260903a-ramp-10-summary.json`과 `stage8c-aws-rtb-capacity-20260903a-ramp-25-summary.json`을 비교한다.

첫 질문: **HTTP 성공률과 p99만 보면 두 번째 시험을 어떻게 판정하겠는가? 그 판정을 바꿀 다른 값은 무엇인가?**

아직 코드나 원인 분석 보고서는 열지 않는다.

### 2. 요청이 어디까지 도달했는지 확인하기

`stage8c-aws-pre-rtb-capacity-20260903a-ramp-25-budget.json`과 `stage8c-aws-post-rtb-capacity-20260903a-ramp-25-budget.json`의 gateway 누적 카운터를 뺀다. 필요하면 최초 10 RPS의 같은 자료로 돌아간다.

질문: 네트워크 전송 실패, DSP의 명시적 응답, 외부 DSP의 성공을 어떤 값으로 구분할 수 있는가?

### 3. 부하량 문제인지 상태 누적 문제인지 구분하기

`stage8c-aws-rtb-capacity-20260903a-recovery-10-summary.json`, 각 구간의 `*-samples.json`, `*-budget.json`을 비교한다. `*-hosts.md`에는 CloudWatch CPU credit도 있다.

질문: 부하를 낮췄을 때 무엇이 회복돼야 자신의 가설이 맞는가? CPU 표본과 전후 스냅샷만으로 알 수 없는 것은 무엇인가?

### 4. 이상 상태에서 코드와 재현으로 이동하기

사용자가 원장과 이벤트 자료에서 이상을 찾은 뒤 `rtb-capacity-20260903a-conflict-diagnostic.json`, `rtb-capacity-20260903a-lease-diagnostic.json`을 연다. 그 다음 관련 코드와 `*-precision-probe.txt`, `*-local-expiry-probe.txt`를 확인한다.

질문: AWS에서 직접 관찰한 사실, 코드에서 가능한 경로, 로컬에서 재현한 현상 중 어느 연결 고리가 아직 입증되지 않았는가?

## 다음 배포가 필요해지는 기준

로컬 자료로 검증할 수 없는 연결 고리를 특정한 뒤에만 결정한다. 실행 전 가설·추가 계측 항목·성공/실패 판정·시간 상한·자동 회수를 먼저 합의한다. 사용자가 실제 대시보드를 관찰할 경우에는 관찰 시간도 함께 정하고, 필요한 자료를 내보낸 뒤 즉시 철거한다.
