# DSP 상세 설계 로드맵

상태: 금액·리스·통지·캠페인 선택·로컬 입찰 실행권·입찰 조정 7A·7B 완료 · 8A 입찰 런타임 조립 기준선 완료 · 8B 운영 어댑터 조립 준비 중

근거: [DSP 컴포넌트](../views/dsp-components.md), [DSP 기술 결정 경계](../technology/dsp.md)

## 현재 위치

아홉 컴포넌트의 책임·메시지·인터페이스는 확정됐다. 다음 작업은 컴포넌트를 다시 나누는 일이 아니라, 각 경계 안의 상태·동시성·복구·기술을 결정하고 구현 가능한 계약으로 좁히는 일이다.

```text
컴포넌트 경계·인터페이스 완료
→ 금액 핵심 상세 설계·구현        완료
→ 리스 생명주기 설계·핵심 구현     완료
→ 통지·복구 상세 설계              완료
→ 예약 통지 증표 발급·검증          완료
→ 캠페인 선택 Hot Path              완료
→ 로컬 입찰 실행권                  완료
→ 입찰 조정 구현·인수 검증            완료
→ 외부 입찰 API·런타임 8A       완료
→ 통지 전송·운영 어댑터 8B       ← 현재
→ SSP 왕복·부하·장애 검증
→ 부하·장애 측정
```

## 현재 시작점

1. `로컬 예산 권한`은 JVM 메모리, 캠페인별 잠금, 다중 `OPEN` 리스와 `DelayQueue` 기준선을 선택했다.
2. 메시지 계약과 구현으로 이 기준선을 검증한다.
3. `리스 생명주기`는 적응형 보충, 로컬 설치, 만료 작업 선점과 멱등 정산까지 구현했다.
4. `경매 결과 처리`는 지역 금액 사건의 최초·중복·충돌 기록과 리스별 재생·자동 정산까지 구현했다.
5. `캠페인 선택`은 슬롯 규격 원시 키, 불변 스냅숏 원자 교체, 실시간 적격성 필터와 결정적 페이싱 순위를 구현했다.
6. `입찰 실행권`은 슬롯 경매 정체성, 요청 의미 지문, 최초 실행권 선점, 중복 즉시 거절과 제한된 기억 수명을 구현했다.
7. `입찰 조정`은 요청·슬롯·후보 워크플로우를 분리하고, sealed 결과 타입과 시간·계속 진행 정책으로 순차 후보 탐색, 슬롯 부분 성공과 요청 중단을 구현했다. 예약 뒤 증표 발급 실패나 응답 여유 소진으로 공개하지 못한 예약은 직접 해제하지 않고 기존 만료 경로로 수렴한다.
8. `OpenRTB 계약`은 메시지·JSON 코덱·입찰 HTTP 어댑터와 Armeria 입찰 전송 기준선을 구현했다. 8A에서 `DefaultDspOpenRtbApi`, `BiddingComponentFactory`, `DspRuntimeSettings`, `DspRuntimeFactory`를 추가해 실행권·입찰 조정·OpenRTB HTTP를 조립했고, 요청 수신 시점부터 `tmax`를 차감하는 실제 HTTP E2E를 통과했다. 다음 8B는 통지 HTTP 경로와 캠페인·리스·키·Outcome 저장소의 운영 어댑터를 붙여 독립 `main`을 만드는 일이다.

리전 예산 원장 선택은 [ADR-010](../decisions/ADR-010-regional-budget-ledger-store.md)에 기록했다.

## 결정 순서

| 순서 | 컴포넌트 | 먼저 다루는 이유 | 예상 산출물 |
|---:|---|---|---|
| 1 | 로컬 예산 권한 | 예약·통지·리스·페이싱이 모두 이 상태와 불변식에 의존한다. | 상태 모델, 동시성 방식, 장애 회복 계약 |
| 2 | 리스 생명주기 | 로컬 권한의 공급·회수와 리전 원장 DBMS 선택을 결정한다. | 원장 DBMS ADR, 리스 발급·정산 계약 |
| 3 | 경매 결과 처리 | `lurl`·`burl` 내구 기록과 로컬 예약 종결의 장애 경계를 닫는다. | 사건 스키마, 기록·재생·백프레셔 계약 |
| 4 | 예약 통지 증표 | 입찰과 통지를 같은 예약에 안전하게 연결한다. | 최소 페이로드, 키 교체·기한 검증 규칙 |
| 5 | 캠페인 선택 | Hot Path 조회 구조와 페이싱 순위를 결정한다. | 캠페인 스냅숏·인덱스·점수 갱신 구조 |
| 6 | 입찰 중복 방지 | 동일 요청의 재실행과 중복 예약을 막는다. | 요청 키·지문·5초 상태·소유자 장애 계약 |
| 7 | 입찰 조정 | 앞선 컴포넌트를 기한 안에서 슬롯별로 조합한다. | 후보 재시도·부분 성공·절대 기한 계약 |
| 8 | OpenRTB 계약 | 내부 의미가 안정된 뒤 외부 JSON·HTTP로 변환한다. | 코덱·HTTP 오류·크기·과부하 계약 |
| 9 | 리전 책임 제어 | 입찰 기능과 리전 리스가 동작한 뒤 전역 예비액 보충을 연결한다. | ADR-003·008의 이전 상태기계 구현안 |

이 순서는 아키텍처 판단 순서다. 실제 코드는 포트와 가짜 구현을 사용해 일부 작업을 병렬화할 수 있다.

## 1. 로컬 예산 권한

### 확정 기준선

- 로컬 DBMS 없이 JVM 힙에 상태를 둔다.
- `ConcurrentHashMap`은 캠페인 계정 조회에만 쓰고 비공정 `ReentrantLock.tryLock()`으로 캠페인별 복합 전이를 보호한다.
- 한 캠페인의 여러 `OPEN` 리스를 허용하고 만료가 가까운 리스부터 사용해 패찰 반환액을 재사용한다.
- 예약은 소속 리스의 일반 해시 인덱스에 두고 검증된 통지와 만료 표식이 캠페인·리스·예약 식별자를 함께 전달한다.
- 전역 `DelayQueue`는 만료 후보만 찾고 지역 사건 저장소의 최초 종결 판정 뒤 금액 상태를 바꾼다.
- 인스턴스 20,000개·캠페인 2,500개를 초기 미종결 예약 상한으로 두며 초과 신규 예약만 거절한다.
- 잠금 대기나 GC가 p99를 침범할 때만 샤드 단일 작성자·오프힙을 다시 비교한다.

### 완료 증거

- 동시 예약 합계가 리스 액면을 넘지 않는다.
- `lurl`·`burl`·만료 경쟁의 금액 효과가 한 번이다.
- 인스턴스를 어느 시점에 종료해도 제한 시간 뒤 소비·반환 합계가 리스 액면과 같다.
- 편향 부하에서 CPU·할당·GC와 예약 p99를 기록한다.

## 2. 리스 생명주기

### 확정 기준선

- 리전마다 독립 PostgreSQL 쓰기 권위를 두고 캠페인 가용액과 리스 발급을 한 트랜잭션으로 바꾼다.
- 같은 발급 요청은 고유 요청 ID로 한 리스만 만들고, 같은 정산은 리스 상태로 한 번만 반영한다.
- DSP는 요청 시작 단조 시각에 원장이 승인한 리스 기간과 안전 여유를 더해 로컬 기한을 만든다. DSP·원장 벽시계 차이는 권한 기간에 영향을 주지 않는다.
- 만료 작업은 `SKIP LOCKED`와 짧은 작업 임대로 여러 DSP 작업자가 나눠 처리한다.

### 구현 상태

- 최근 예약량과 가까운 만료를 사용해 보충 요청액을 가변 계산한다.
- 원장 발급 성공 뒤 같은 DSP의 로컬 권한에 설치하고 설치 실패를 성공으로 보고하지 않는다.
- `safeRecoveryAt` 이후 원장 리스 행을 정산 작업으로 선점하고 액면 전액을 확정·반환·격리로 분류한다.
- 서울·도쿄 독립 PostgreSQL 개발 환경과 발급·정산 통합 시험을 제공한다.
- 지역 금액 사건을 재생하는 `LeaseEventReader`와 보충·정산 주기 실행기를 연결했다.

### 완료 증거

- 동시 발급·중복 요청·중복 정산에서 리전 책임액을 넘지 않는다.
- 원장·네트워크·DSP 장애 각 지점에서 같은 리스를 두 번 활성화하지 않는다.
- 원장 중단 중 기존 로컬 리스 입찰은 계속되고 새 보충만 멈춘다.

## 3. 경매 결과 처리

### 확정 기준선

- 검증된 `lurl`·`burl`과 예약 만료를 지역 PostgreSQL에 기록한 뒤 로컬 예약을 종결한다.
- 예약별 최초 종결을 금액 결과로 소유하고 같은 사건은 중복, 반대 결과는 충돌로 기록한다.
- 기록 뒤 로컬 반영 전에 장애가 나면 같은 사건을 재생해 멱등 종결한다.
- 정상 기한의 `burl`만 확정하고 충돌 금액은 격리하며 나머지 리스 액면은 반환한다.
- 저장 실패는 성공으로 응답하지 않고 같은 만료 사건과 정산 작업을 재시도한다.

### 완료 증거

- 성공 응답한 `lurl`·`burl`은 재시작 뒤 복구된다.
- 기록 직후 장애와 응답 유실 뒤 재호출에서도 금액 효과가 한 번이다.
- 통지 적체가 입찰 실행 자원을 무제한 점유하지 않는다.

## 4. 예약 통지 증표

### 현재 구현

- 발급과 검증 인터페이스를 분리했다.
- 인증된 SSP·발급 리전·예약 사실을 공통 증표 내용으로 구성한다.
- `WIN`·`LOSS`·`BILLING` 종류를 포함해 AES-256-GCM으로 봉인한다.
- 형식 버전·키 ID·96비트 nonce·암호문을 Base64URL 증표로 만든다.
- 발급 리전의 DSP만 해당 증표를 처리하며 리전 장애 시 예약 만료와 리스 정산으로 회수한다.

### 테스트 학습과 검증 순서

각 단계는 개념을 이해하고 현재 코드에서 확인한 뒤 다음 단계로 넘어간다.

1. JUnit Platform·Jupiter·TestEngine이 맡는 역할과 실행 계층을 이해한다.
2. Gradle이 테스트를 컴파일·발견·선택·실행하고 결과를 수집하는 과정을 추적한다.
3. 테스트 클래스 인스턴스와 `PER_METHOD`·`PER_CLASS` 생명주기를 이해한다.
4. `@Test` 등 어노테이션이 테스트 설명자와 실행 작업으로 변환되는 과정을 이해한다.
5. Assertion이 실패를 표현하는 방식과 예외·원인 검증의 경계를 이해한다.
6. JUnit 5 Extension Model의 콜백·매개변수 주입·상태 저장 구조를 이해한다.
7. 암호 테스트에서 키·nonce·시간을 결정적으로 통제하면서 운영 난수 경계를 보존하는 법을 익힌다.
8. 이진 형식 단위 시험, 봉인 계약 시험, 발급 조정 시험, 왕복 통합 시험의 경계를 나눈다.
9. 내부 구현 순서보다 왕복 보존·비결정성·변조 거부·종류 및 신뢰 경계 같은 보안 성질을 시험한다.
10. 합의한 시험을 구현하고 전체 회귀 시험을 통과시킨 뒤 `ReservationNoticeVerifier` 구현으로 넘어간다.

### 반드시 결정

- 예약 ID·리스 ID·세대·캠페인·금액·예약 기한 중 외부 토큰에 반드시 들어갈 값을 정한다.
- `nurl`, `lurl`, `burl` 종류를 바꿔 호출할 수 없게 종류를 인증 범위에 넣는다.
- 페이로드 버전, AEAD 키 ID, 현재·이전 검증 키의 교체 규칙을 정한다.
- Base64URL을 포함한 최대 URL 길이와 요청당 발급 비용을 측정한다.

### 완료 증거

- 변조·다른 통지 종류·다른 리전·기한 경계를 모두 거부한다.
- 키 교체 중 기존 5초 토큰을 검증할 수 있다.
- 발급·검증이 입찰 p99를 침범하지 않는다.

## 5. 캠페인 선택

### 현재 구현

- `SlotDimensionPacker`: 광고 슬롯 규격(width, height)을 64비트 원시 `long` 키 1개로 Zero-Allocation 비트 패킹/언패킹 및 부호 오염 방어.
- `DefaultCampaignRuntime`:
  - L1 캐시 친화적 `long[] sortedDimensionKeys` 및 `IndexedCreative[][]` 버킷 인덱스를 빌드하여 `Arrays.binarySearch` 기반 5ns 무락 서빙.
  - `AtomicReference` 기반 CAS (`compareAndSet`) 루프로 스냅샷 갱신 시 단조 증가 버전 보장 및 Lost Update 방지.
  - 자연수 버전 비교(`compareVersions`)로 `"v10" > "v2"` 올바른 업그레이드 지원.
  - 반열린 시간 구간 `[startsAt, endsAt)` 및 매체사 바닥가(`bidCpm >= bidFloor`) 실시간 적격성 필터링.
  - `CampaignPacingSource` 연동: 1차 `pacingLagPpm` 내림차순, 2차 `campaignId` 오름차순 결정론적 순위화.
  - 단일 후보 즉시 반환 및 전원 탈락 시 `List.of()` 무할당 반환.

### 반드시 결정

- 캠페인 외부 ID를 정수 실행 인덱스로 변환하는 적재 구조를 정한다.
- 슬롯 규격별 후보 배열과 캠페인·소재의 메모리 배치를 정한다.
- 페이싱 지연 점수의 입력, 갱신 주기와 원자 공개 방식을 정한다.
- 같은 점수에서 `campaignId` 순서를 보존한다.
- 1순위 예약 경합 실패 뒤 다음 후보를 어디까지 시도할지 기한 기준으로 정한다.

### 완료 증거

- 10만 캠페인·활성 3만·후보 p99 1,000개에서 조회 비용과 메모리 크기를 기록한다.
- 스냅숏 교체 중 부분 버전이 보이지 않는다.
- 오래된 페이싱 투영이 예산 초과를 만들지 않고 분포 오차로만 남는다.

## 6. 입찰 실행권

### 현재 구현

- `SlotAuctionKey`는 인증된 `sspId + requestId + impressionId`로 슬롯 경매를 구조적으로 식별한다.
- `Sha256BidRequestFingerprintCalculator`는 요청 ID와 슬롯 배열 순서를 제외하고 `tmax`와 슬롯 집합·규격·바닥가·노출 기한을 결정적 버전형 SHA-256으로 묶는다.
- `DefaultBidExecutionGate`는 `ConcurrentHashMap.putIfAbsent`로 같은 `sspId + requestId`의 최초 호출 하나에만 실행권을 준다.
- 같은 키·지문의 진행 중·완료·불확실 후속 요청은 최초 결과를 기다리거나 재사용하지 않고 `DUPLICATE_REQUEST`로 즉시 거절한다. 같은 키·다른 지문은 `REQUEST_CONFLICT`다.
- 최초 실행 실패도 실행권을 소비하며 기억 수명 안에서 재실행하지 않는다. 진행 중 엔트리는 기억 수명이 지나도 교체하지 않는다.
- 종결 엔트리는 단조 시계 기억 경계에서 우선순위 만료 표식으로 제거한다. 원자 용량 계수는 동시 신규 키 경쟁에서도 기본 100,000개 상한을 넘지 않고 만료 뒤 용량을 회복한다.

### 반드시 결정

- 요청 키를 `sspId + BidRequest.id`로, 내용 충돌을 요청 지문으로 판정한다.
- 실행권 기억 수명과 메모리 상한을 운영 측정으로 조정한다.
- DSP 게이트웨이의 안정된 소유자 라우팅 알고리즘과 노드 목록 세대를 정한다.
- 소유 인스턴스 장애 때 결과를 모르면 새 예약을 만들지 않는 실패 응답을 정한다.
- 계획된 축소에서 기존 요청 상태를 보존할 drain 시간을 정한다.

### 완료 증거

- 동시 중복 요청 중 하나만 캠페인 선택·예약을 실행하고 나머지는 기다리지 않고 거절한다.
- 같은 키의 다른 내용은 거부한다.
- 노드 증감·장애 중 소유권이 불확실한 요청을 재실행하지 않는다.

## 7. 입찰 조정

### 현재 구현

- `DefaultBidCoordinator`는 슬롯을 요청 순서대로 처리하고 완성된 입찰만 모으며, 정상 무입찰은 다른 슬롯과 격리한다.
- `DefaultSlotBidWorkflow`는 순위 후보를 순차 탐색하고 예약 거절을 다음 후보·슬롯 중단·요청 중단으로 타입화한다.
- `DefaultCandidateBidAttempt`는 후보 하나의 예약과 세 통지 URL 발급을 결합하며 둘이 모두 성공한 경우에만 `PreparedBid`를 만든다.
- sealed 결과 타입은 `Prepared`·`NoBid`·`HaltRequest`와 `AttemptPrepared`·`AttemptRejected`·`AttemptAbandoned` 상태를 완전하게 표현한다.
- `DeadlineBidTimePolicy`는 고정 후보 횟수 대신 예상 후보 비용과 응답 여유를 단조 시계 절대 기한에 비교한다.
- 예약 뒤 증표 발급 실패, 계약 불일치나 최종 응답 여유 소진으로 공개하지 못한 예약은 금액 권위를 직접 바꾸지 않고 5초 만료 경로로 수렴한다.
- 첫 기준선은 동기 로컬 호출을 슬롯·후보 순서대로 실행한다. 병렬화는 순차 기준선 측정이 요구를 만족하지 못할 때만 비교한다.
- [7B 인프로세스 인수 검증](dsp-bid-coordination-acceptance.md)은 실제 Campaign Runtime·Local Spending Authority·AES-GCM Proof를 조립해 예약과 세 증표의 동일성, 슬롯 부분 성공과 공개되지 않은 예약의 만료 반환을 확인한다.

### 완료 증거

- 여러 슬롯과 후보 경합에서도 기한 뒤 입찰을 반환하지 않는다.
- 반환한 모든 입찰에는 예약과 세 통지 URL이 하나씩 있다.
- 예약하지 못한 슬롯만 빠지고 다른 슬롯은 정상 응답한다.
- 단위 시험은 후보 재시도, 인스턴스 포화 중단, 슬롯 부분 성공과 응답 여유 소진을 검증한다.
- 7B 인수 시험은 실제 예약·실제 세 증표, 실제 부분 성공과 예약 후 Proof 실패의 만료 수렴을 검증한다.
- 실제 SSP HTTP 왕복과 응답 직전 전송 기한 경계는 8단계 DSP 실행 조립 E2E에서 검증한다.

## 8. OpenRTB 계약

### 현재 분할

| 세부 단계 | 책임 | 상태 |
|---|---|---|
| 8A 입찰 런타임 조립 | Bidding 실행 파사드, OpenRTB 애플리케이션 서비스, 검증된 실행 설정, HTTP 수직 E2E | 완료 |
| 8B 운영 어댑터 조립 | 통지 HTTP 라우트, 캠페인 스냅숏·리스 공급·키 소스·Outcome DB 생성, 배경 작업자, `DspApplication.main` | 다음 |
| 8C 운영 검증 | SSP 코덱 실제 왕복, p99 부하, 포화·DB 장애·종료 검증 | 대기 |

8A의 `DspRuntimeFactory.Components`는 캠페인 선택·로컬 예산·Proof·Outcome의 공개 포트만 받는다. 이 경계로 Bidding의 `internal` 타입이 조립 루트로 누출되지 않고, 아직 없는 운영 공급자를 빈 구현으로 위장하지 않는다. 상세 근거는 [DSP 런타임 8A 조립](dsp-runtime-assembly.md)에 기록한다.

### 반드시 결정

- DSP HTTP 서버와 JSON 기준선 기술을 선택한다.
- OpenRTB 2.6 하위 규격의 필수·거부 필드, KRW 변환과 2초 `exp`를 구현한다.
- 본문 크기, 처리 중 요청, 대기열, 연결과 파싱 상한을 정한다.
- 실제 입찰은 HTTP 200 `BidResponse.seatbid`, 사유 있는 무입찰은 HTTP 200 `BidResponse.nbr`, 사유 없는 무입찰은 HTTP 204로 표현한다.
- 잘못된 요청, 포화와 내부 실패의 HTTP 표현을 정한다.
- 입찰과 통지 경로의 실행 자원을 처음부터 분리할지 측정 뒤 분리할지 정한다.

### 완료 증거

- SSP 코덱과 실제 HTTP로 왕복해도 가격·슬롯·통지 의미가 같다.
- 잘못된 형식과 과부하를 빠르게 거절하고 정상 요청의 p99를 보호한다.
- JSON을 이후 이진 표현으로 바꿔도 내부 메시지와 컴포넌트 계약은 유지된다.

## 9. 리전 책임 제어

### 기존 ADR을 구현으로 좁힐 문제

- 부족 감지 임계치와 이전 요청 단위를 운영 설정으로 둔다.
- 전역 준비·지역 활성화·전역 완료의 상태와 재시도 키를 정의한다.
- 이전 중 격리액을 어느 쪽도 사용하지 못하게 한다.
- 전역 원장 장애 중 자동 승격 없이 지역 리스가 계속되는지 연결한다.
- 다른 리전의 금액은 미사용 반환을 증명한 뒤에만 이전한다.

### 완료 증거

- 단계마다 요청·응답을 중복·유실하고 프로세스를 종료해도 한 금액이 두 리전에 활성화되지 않는다.
- 전역 원장 중단이 기존 지역 리스와 입찰을 중단시키지 않는다.
